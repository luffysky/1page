## 一、CR-007：CRM 從 Excel／CSV 匯入

Luffy 的話是「CRM設計加上匯入excel csv功能 值的類別看有沒有辦法正確判斷
**或者讓使用者後面可以修改** 填資料也可以匯入excel或csv」。

粗體那半句才是規格：猜完之後那份結果是**可編輯的草稿**，不是既成事實。

### 兩條路

```text
/crm 設計器          從檔案建一類：猜型別 → 逐欄可改 → 加進設計
/account/crm/[id]    批次匯入資料：欄名自動配對 → 逐列驗證 → 送出
```

### 不加執行期依賴

整個專案只有十個執行期依賴，加一個是一個真實的決定。
最常見的那個 xlsx 套件在 npm 上已標為 deprecated 且有過 CVE，
而我們要的只是「把第一張工作表讀成格子」。

```text
.csv    自己寫 RFC 4180。失敗模式很具體：分隔符在引號裡、
        換行在引號裡、Excel 的 BOM——三件用 split(",") 一定錯，
        而錯的樣子是安靜的（一列變兩列、一格變兩格）
.xlsx   一個 ZIP + 兩份 XML。用瀏覽器原生的 DecompressionStream 讀。
        只讀第一張工作表——多張時不猜是哪一張
.xls    讀不了，也不假裝讀得了。檔頭是 D0 CF 11 E0，明確擋下來並說
        「請另存成 .xlsx 或 CSV」
```

### 三件不能安靜出錯的事

```text
電話不能變數字     0912345678 存成 number 會掉開頭的 0，
                  而 912345678 看起來完全正常
斜線日期要轉 ISO   2026/8/18 過不了 YYYY-MM-DD。不轉的話畫面說是日期、
                  每一列卻都匯入失敗——使用者什麼都沒做錯
壞掉的列要指名     匯入其餘的，逐列說出第幾列哪一欄不對，
                  而且要在**按下送出之前**看得到。列號與 Excel 一致
```

### 檔案不上傳

在瀏覽器裡讀完，只送對應好的那幾列值。少一條上傳路徑就少一整類問題。
代價是相信不了瀏覽器送來的東西——所以伺服器用**與手動新增同一份**
`recordSchemaFor` 逐筆重驗，而且整批一次 insert（分次的話第 180 筆
撞上限會留下前面 179 筆，而使用者不會知道要去刪）。

### 自己抓到的五個假綠燈

每一條測試寫完都故意把程式改壞一次。這一輪抓到五個：

```text
BOM 那條驗錯層次    驗的是 toSheet，而 U+FEFF 在 JS 裡算空白字元，
                    `.trim()` 本來就吃掉它。把 csv.ts 裡處理 BOM 的
                    那一整段拿掉，十五條測試照樣全過。改釘 parseDelimited

「要有重複」是死的   select 的 `distinct < filled` 永遠成立
                    （比例條件已經含蘊它）。拿掉它測試不會紅——
                    那一行從來沒有擋過任何東西

兩條路徑走不到      xlsx 的 26 進位欄名（AA 之後）與 rich text
                    （一格裡有粗體會被切成好幾個 <t>），fixture 產不出來，
                    所以改壞了也不紅。補進 fixture 才驗得到。
                    ⚠️ 26 進位算錯的後果是第 27 欄的值蓋掉第 2 欄——
                    損壞發生在使用者看得到的前幾欄

strip 幫忙擋掉了     「不匯入的欄位」用了一個定義裡根本沒有的欄位當例子，
                    `recordSchemaFor` 的 `.strip()` 順手清掉了

「不太確定」到處都是  六欄裡三欄掛著提醒＝沒有提醒。改成只標
                    **猜錯會有代價**的（0/1 猜成勾選、樣本太少的下拉）。
                    文字是安全的預設：什麼都收得下，猜「錯」也不會弄丟東西
```

### e2e 抓到一個單元測試抓不到的

換一個類別的時候，已經讀進來的對應表原封不動留著——而兩類都是匯入建的話
欄位 id 都是 `col-1`、`col-2`，於是電話會填進金額欄，畫面上完全看不出來。

現在讀進來的表**綁著它是為哪一類讀的**，換類別就當作沒選過檔案。
那是實話：對應是對著某一組欄位做的，換了一組就不成立。

## 二、收尾稽核：API / DB / UI / RWD / PWA

Luffy 交辦全面清查。做法是逐項去問，不是憑印象。

### 兩件真的壞的

**① `adminListUrl`** —— 一個從 2E 就存在的 Server Action：沒有呼叫點、
沒有驗身分，而它回傳的是後台的密路徑。

Server Action 不是「那個頁面才叫得到的函式」，它是一個**公開端點**。
沒有呼叫點不代表它不存在，只代表沒有人記得它還在。已刪除。

**② CRM 記錄頁整頁會橫向捲 39px** —— 表格的溢出寬度會傳到 documentElement
（`html.scrollWidth` 429、`body` 390）。實測 `overflow-x: hidden` 也擋不住，
只有 `contain: paint` 擋得住。

這正是 Luffy 當初講的那件事：「別整個 div 一起動」。當時做了 sticky 與
內層捲動，但**整頁仍然推得動**，而守著這件事的那條測試是假的（見下）。

### ⚠️ `scroll-behavior: smooth` 讓每一個捲動檢查都變成假的

```text
window.scrollTo(9999, 0);
const x = window.scrollX;   // 永遠是 0——捲動是動畫的，還沒捲完
```

站台的 `<html>` 上有 `scroll-behavior: smooth`。於是任何「推推看有沒有動」
的檢查都永遠量到 0，也就永遠不會紅。

發現的方式：新寫的公開路由斷點測試，故意在 `/pricing` 塞一個 1600px 寬的
東西進去，**八個斷點全綠**。改成 `behavior: "instant"` 之後紅了七個
（1920px 那個本來就不該紅）。

回頭去看，CRM 記錄頁那條「整頁不得橫向捲」也是同一個寫法——
它從來沒有擋過任何東西，而它要擋的那件事**當時就已經在發生了**。

還有一件相關的：之前把 `documentElement.scrollWidth` 量到的 429 當成
「捲動容器灌水」而略過。灌水是真的，但那一頁**同時**真的溢出 39px。
兩個原因湊在一起，剛好互相掩護。

### 新增五個守衛，問法一律是反過來的

不列「應該有哪幾個」，而是問「**有沒有哪一個沒有**」。
前者每次新增都要記得補，後者會自己發現下一個。

```text
server-action-wiring   每個 action 都有呼叫點、都驗身分（unit）
rls-coverage           去 pg_tables 問有哪些表開了 RLS，逐一敲（db）
sitemap-coverage       公開路由有沒有哪一條不在 sitemap（unit）
public-breakpoints     九條公開路由 × 八斷點 = 72 條（e2e）
pwa                    manifest 的每個圖示、maskable、apple-touch-icon（e2e）
```

`rls-coverage` 那個特別要說一下：**只驗「匿名讀不讀得到」會被空表騙過**——
讀到零筆與被擋下來長得一模一樣。一張政策寫成 `true` 的空表會安靜過關，
等到有資料的那天才開始漏。所以另外驗政策本身有沒有無條件的 `true`，
與資料多寡無關。實測在 `invoices` 上加一條 `using (true)` 會紅。

## 三、留給 Luffy 的一件裁決

`/crm` 設計器的匯入**只建結構**，資料要到記錄頁用同一個檔案再選一次。
做成一次的話，設計器與記錄頁之間要保住那份已解析的資料，
而它要活過「存檔 → 導頁 → 新的 id」這一整段——中間任何一步失敗，
畫面上會是「資料好像匯進去了」而其實沒有，那比多選一次檔案糟。

兩邊都說得通，所以沒有自己決定。已記在待辦。
