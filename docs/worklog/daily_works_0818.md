## 一、`thumbnail_url`：移除，不是接上

待辦寫著「要接一條產生縮圖的路徑（瀏覽器端縮圖再傳第二份，
或接 Cloudflare Images）」。去讀了程式才發現它比想像的更空：

```text
寫入端   沒有。上傳流程從來不產生縮圖
讀取端   supabase-repository 有把它映射成 thumbnailUrl……
         但**沒有任何元件在畫它**
```

兩端都沒有。而真的去接的話會疊出**第二套更差的機制**——
`next/image` 的最佳化器本來就依 `sizes` 產出對的尺寸，
作品卡片已經在用了。

### 它掩蓋掉的真問題

作品詳細頁的相簿用的是原生 `<img>`，帶著一行 `eslint-disable`：

```tsx
{/* eslint-disable-next-line @next/next/no-img-element */}
<img src={media.url} alt={media.alt} className="w-full" />
```

沒有寬高的圖片在載入時會把下面的內容整個推開（CLS），
而那是 `audit:perf` 在盯的數字之一。那一行 disable 就是味道所在。

### 所以存的是原始尺寸，不是另一份檔案

`width` / `height` 兩個整數，由瀏覽器在上傳成功之後量
（`createImageBitmap`，量完 `close()` —— 一張 4000×3000 的
ImageBitmap 佔 48MB 解碼後記憶體，連傳十張不關會被系統殺掉）。

**量不出來就回 null，不猜。** 猜一個尺寸的話 next/image 會依那個
比例留位置，圖片載入後再跳一次——那比完全不給更糟，
因為不給的時候渲染端知道要走 fallback。

```sql
check ((width is null) = (height is null))
```

成對，或都不給。只知道一邊的話長寬比算不出來，
而 next/image 需要的正是長寬比。**驗證方式**：只塞 width 進去，
資料庫回 `violates check constraint "media_dimensions_paired"`。

⚠️ 這張表目前 0 筆，所以不需要回填。有幾千筆之後才做的話，
這就不再是「加兩個欄位」而是一次資料遷移——
與 SSO 那件事「趁媒體記錄還很少的現在做」是同一個判斷。

## 二、CR-003-5：前台的 CRM 設計器

CR-004 最後一段。`/crm`，導覽列「設計 CRM」。

**定價與網站編輯器一致**：設計免費、不用登入（狀態在 sessionStorage），
存下來才要帳號。匯出 JSON 也免費——那是使用者自己設計的東西，
扣住它當人質不會讓人更想付錢，只會讓人覺得被坑。

### 絕對不下 DDL

```text
「他定義一張表，我們就 create table」＝ 把 DDL 權限交給不可信輸入
  表名來自使用者輸入
  改一個欄位就是一次線上 migration
  幾百個使用者之後 schema 裡有幾千張沒有人看得懂的表
```

一張表配 jsonb，RLS 一條。代價是查詢能力弱——
但這是「設計一個 CRM 給自己用」，不是資料倉儲。

### 不是重寫一個編輯器，是換一組 widget

搬動的規則從 preview-context 裡抽出來成 `lib/reorder` 的 `moveInOrder`，
兩邊共用。拖曳**一步一步呼叫它走過去**，不另外寫「移到第 N 位」——
兩條改順序的路徑遲早會在邊界條件上不一致（最常見的是往下拖時
索引要不要減一），而不一致的表現正是拖曳與鍵盤結果不同。

**驗證方式**：把拖曳改成經典的 off-by-one，「鍵盤與拖曳走到同一個結果」紅了。

### ⚠️ 記錄的擁有權：兩層，而且各自都要站得住

`crm_records` 有兩個擁有者概念：記錄自己的 `owner_id`，
以及它掛在誰的定義底下。不一致的話，一個人就能往別人的 CRM 裡寫資料。

實測過三種組合：

```text
policy 只驗 owner_id ＋ 有 trigger    擋得住，但**是 trigger 擋的**
policy 只驗 owner_id ＋ 沒 trigger    ❌ B 真的把記錄寫進 A 的 CRM
policy 問 definition 擁有權 ＋ 沒 trigger  擋得住
```

第二行是實際跑出來的，不是推測。所以 insert policy 問的是
**「你有沒有這份定義的擁有權」**，不是「你有沒有把自己的 id 填對」。

只留 owner_id 那一版的話，整個邊界會**押在一個 trigger 上**——
而 trigger 是為了資料一致性寫的，不是為了擋人。哪天有人為了效能
把它換成應用層填值，安全性就跟著沒了，而且不會有任何東西報錯。

### e2e 抓到兩個單元測試沒抓到的東西

```text
無限重繪              SaveBar 的 onSaved 是 inline 箭頭函式，
                      每次 render 都是新身分 → effect 每次都跑 →
                      dispatch → 再 render。瀏覽器 console 噴
                      Maximum update depth exceeded。
                      網站編輯器沒踩到，是因為它的 setSavedSite
                      來自 useMemo 過的 context value

必填收得下空字串       `z.string()` 讓 "" 過關，所以「必填」在伺服器端
                      **等於不存在**——而瀏覽器那個 required
                      按一下 F12 就沒了。表現是一筆每一格都空白、
                      卻通過驗證的記錄
```

兩個都補了單元測試（那一層跑一次一秒，e2e 那一條要一分鐘）。

## 三、又寫了一個假守衛，這次自己抓到

「沒填的數字欄位不會變成 0」——`z.coerce.number()` 會把 `""` 變成 **0**，
而在一份記價格或數量的 CRM 裡那個 0 看起來完全正常。

寫完之後照規矩把 preprocess 整個拿掉，**測試照樣綠**。

原因是那條測試用的是**選填**的數字欄位，而選填在外層就已經把空字串
轉成 undefined 了——裡層那道防線根本沒被走到。真正會安靜存成 0 的
是**必填**的數字欄位。

加了一個必填的數字欄位進去，再拿掉 preprocess，紅了。

> 每加一個守衛，就故意把程式改壞一次。這一天靠這條規矩抓到
> 一個自己寫的假守衛，以及上面那個必填空字串的洞。
