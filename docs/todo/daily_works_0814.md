## 一、這一天最重要的一件事

**媒體上傳從來沒有在瀏覽器裡成功過。**

從 CR-001 做完到今天，`portfolio_media` 一筆資料都沒有。三層都擋著，
而三層都不會產生伺服器錯誤：

```text
1. next.config 沒有 images.remotePatterns
   next/image 對外部主機是白名單制，不在名單上的直接丟例外——整頁 500。
   r2.ts 有一個 publicHostnames()，註解寫著「供 next.config 與測試取得」，
   而 next.config 從來沒有呼叫它。零呼叫點。

2. CSP 的 connect-src 沒有 R2 的 S3 端點
   上傳是瀏覽器直接 PUT 到 <bucket>.<account>.r2.cloudflarestorage.com，
   跟公開讀取的媒體網域是兩個不同的名字。0813 加 CSP 那天擋掉了它。

3. R2 bucket 沒有 CORS 設定
   preflight 過不了，請求根本送不出去。
```

**為什麼一直沒被發現**：兩個驗證方式剛好都繞過了它。
`pnpm test:db` 的上傳測試是從 Node 發的，Node 不做 CORS；
後台的作品上傳沒有人從瀏覽器真的跑過一次。

而 21 項 security 稽核沒有一項在問「加了 CSP 之後既有功能還能不能用」。
CSP 擋掉請求時不會有伺服器錯誤——畫面只說「上傳失敗，請檢查網路」。

第 1、2 項已修，第 3 項要在 Cloudflare 後台設（見 `scripts/r2-cors.mjs`）。

## 二、編輯器補完

### 草稿載回編輯器

存檔功能原本**只寫不讀**。`saved_sites` 存的是 `buildSiteConfig()` 算出來的
成品，而成品裡沒有「當初選的是哪一套模板」——那個資訊在算出成品的
那一刻就被丟掉了。存得進去、永遠打不開；會員中心的清單只證明資料進去了。

改成存輸入。資料庫與 sessionStorage 現在是同一份文件、同一個 schema
（`editor-state.ts`）——**兩邊各存各的形狀正是這次載不回來的原因**。

```text
/edit?draft=<id>          入口在會員中心的「編輯」
再按存檔＝更新那一份       另有「另存新的一份」
載不到時明講              不安靜地退回一份空白版型
未登入點草稿網址          導向登入，不是說東西不見了
```

### 新增／刪除單一項目

模板給三個服務、使用者有四個，那第四個原本永遠加不上去。
一個「幾乎可以用」的編輯器比明顯不能用的更氣人。

刪到剩一項停手。**不是為了留內容**，是因為欄位形狀是從現在的值認出來的：
空陣列既是空字串清單也是空項目清單，分不出來——刪光之後
「新增一個」加出來的會是錯的形狀，那一塊直接不見。

動詞也分開了：整塊叫「移除」，單項叫「刪除」。兩顆都寫「移除」的話，
使用者按下去之前分不出會少一項還是少一整塊。

### 圖片上傳

作品區塊原本是色塊佔位。上傳一定要登入——這條線與存檔那條不同：
存檔是定價（免費編輯、存檔才付費），**上傳是安全**：
不檢查身分的 presign 端點等於開放公開寫入，而 R2 沒有 RLS。

圖片來源改成白名單（只認自己的媒體網域）。順帶發現
`brand.logo` 的註解本來就寫著「走與其他媒體相同的來源限制」，
而它用的是 `externalUrl`——**任何 https 都收**，那句話在程式上從來沒成立過。

## 三、接線補完

### 分類清單

2D 的註解寫著「換上真實資料庫後改由 DB 供應」，而那件事一直沒做：
資料表有 11 筆種子、篩選器讀的是硬編陣列，兩份剛好一樣，
但沒有任何機制保證它們維持一樣。

現在畫面讀資料庫，程式碼那份退成種子，`test:db` 比對兩者。

⚠️ 過程中我自己也犯了一次同樣的錯：加了 `.eq("active", true)` 並註明
「active 沒有任何讀取端」。**那是錯的**——RLS policy
`using (active or is_admin())` 就是它的讀取端，而這支查詢走沒有 session 的
anon client，資料庫那層早就擋掉了。把那行拿掉測試照樣綠，
所以它從頭到尾沒擋過任何東西。已移除並在程式碼裡寫明。

（`audit:wiring`【3】把 `active` 列為未接線是誤報：它只掃 TS，看不到 SQL policy。）

### Tag 與 Service 篩選

Spec §8.7 列了「另可依 … Tag / Service 篩選」，之前只做了 Category + Project Type。
`portfolio_project_tags` 的 join 終於有讀取端。

篩選器改成**一份狀態物件**，不是每個維度各一個 `useState`：
四個維度時原本的寫法會開始出錯，每個 `chooseX` 都要記得把其他三個現值
傳進 `commit`，漏掉的那個會在切換時被重設成「不限」。

「更多篩選」的 details 用受控 state + `onToggle`，不是 `open={條件}`——
後者讓使用者手動展開之後，下一次 `router.push` 的重新渲染會把它關回去。

### 後台可編輯 Case Study

`case_study_json` / `links_json` / `ai_disclosure_json` 從 2E 起就在 schema 與
公開頁面裡完整支援，後台表單卻只有基本欄位——**只能直接改資料庫**。
那是「有讀取端、沒有寫入端」。

⚠️ 踩到一個只有用真資料才問得出來的問題：連結欄位我用了 `type="url"`，
而 `interior-studio` 的 demo 連結是站內路徑 `/work/interior-studio`。
**打開那件作品、什麼都不改、按儲存就會失敗**，而瀏覽器只給一個氣泡提示，
畫面上沒有任何我們自己的錯誤訊息。測試看到的是「等待導頁逾時」。

改成站內路徑或 https 都收（與 SiteConfig 的 `linkTarget` 同一條規則），
並在 e2e 裡加一條「送出前確認沒有欄位被瀏覽器判為無效」。

## 四、守衛本身的修正

### 可達性檢查帶已登入 session（ME）

`audit:wiring`【8】的爬蟲是匿名的，看不到只給登入者的入口。
0813 真的因此漏過一次（`/account`）。後台整組也在例外清單裡，
理由是「路徑要保密」——那個理由對公開頁面成立，對後台自己不成立。

`authed-reachability.spec.ts` 帶真的 session 爬兩次：
會員登入後從 `/` 走得到 `/account`；員工從後台首頁走得到每一個 `/admin/**`。

### audit:wiring【3】掃的是五個寫死的檔案

那是 2D 當時所有會碰資料庫的地方。之後新增的 leads、profiles、
saved_sites、會員中心的 actions **全部不在清單上**，於是它們用到的欄位
一律被報成「沒有任何程式碼取用」——owner_id、display_name、contact_email
都是誤報。

**一份大半是誤報的警告比沒有這條警告更糟**：下次真的有欄位沒接線時，
沒有人會多看一眼。這是「守衛通過不等於守衛有效」的另一面——
守衛在叫，但叫的內容是假的。

改成掃整個 src（173 個檔案），實際取用的欄位從 20 變成 37，
剩下五個具名例外各自寫了理由。驗證方式：加一個沒有人讀的欄位 → 立刻被指名。

### 一個我自己寫的假守衛

`site-renderer.test.tsx` 的「兩個同名項目都畫得出來」——
React 首次渲染本來就會把重複 key 的兩個孩子都畫出來，
把 key 改回 `item.label` 照樣綠。重複 key 真正壞掉的地方是**更新**，
而那是編輯器每打一個字都會走的路徑。改成驗 React 自己的重複 key 警告。

### migration 帳本與現實脫節

`pnpm db:push` 今天第一次重跑就整個卡住：`_migrations` 少了 0007／0008 兩筆，
因為 0813 那兩個 migration 是繞過 db-push 直接套用的。
表存在、RLS 開著、policy 都在，只有帳本沒記。已補上。
